# Taskboard

A responsive, server-rendered task manager for **PHP 8.4**. Create, edit, complete,
reopen, and delete tasks, with MySQL storage and no frontend build step,
Laravel, or third-party packages.

## Task organization

- Set low, medium, or high priorities when creating or editing tasks.
- Add an optional due date; unfinished tasks past their due date are marked overdue.
  Dates use the PHP server's configured timezone (UTC by default).
- Search titles and descriptions, and filter by all, in-progress, or completed tasks.
  Search text is matched literally, including `%` and `_`.
- Searches and status filters work together and remain selected while editing,
  completing, or deleting tasks. Summary counts always reflect the entire task list.

## Requirements

- PHP 8.4 with the PDO and PDO MySQL extensions enabled.
- MySQL 8.0.16 or later (MySQL 8.4 LTS recommended).

## Run locally

Use your existing MySQL server; no additional server or service is required.
Create a separate database named `taskboard_php84` with the `utf8mb4` character set,
and grant your application account access to that database only. Do not reuse another
application's database.

Copy `config/database.example.php` to `config/database.local.php` and enter your
connection details. The local file is ignored by Git. Environment variables
`DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, and `DB_PASSWORD` override the
local configuration. Defaults are `127.0.0.1:3306` and database `taskboard_php84`.
PHP does not automatically load `.env` files.

For TLS-enabled servers, set `ssl_ca` in the local configuration (or `DB_SSL_CA`)
to the CA certificate path. Certificate verification is enabled by default.
This machine's existing server uses an autogenerated certificate without a matching
hostname; its approved local configuration sets `ssl_verify_server_cert` to `false`
while retaining TLS encryption. This exception is restricted to literal loopback
addresses and requires a CA file. Use a valid matching certificate and verification
for remote or production connections.

On Windows, enable `extension=pdo_mysql` and configure `extension_dir` in `php.ini`
if your PHP distribution does not enable MySQL by default.

From the repository root, initialize the application's table and start PHP:

```powershell
php scripts\setup.php
php -S 127.0.0.1:8000 -t public
```

Open <http://127.0.0.1:8000>. Composer is optional; `composer setup` and
`composer start` run the same commands. Setup creates the table if missing; it does
not drop existing tables. The web application only needs SELECT, INSERT, UPDATE,
and DELETE permissions after setup.

The application no longer reads SQLite. Any previous `storage/tasks.sqlite` file
is left untouched as a backup; existing data is not automatically imported.

## Tests

Create a separate, empty MySQL database named `taskboard_php84_test` and grant
the test account access to it, including CREATE for the test table. Then run:

```powershell
$env:DB_DATABASE = 'taskboard_php84_test'
php tests\run.php
Remove-Item Env:DB_DATABASE
```

Other connection settings use the same local configuration or environment variables.
Tests refuse database names that do not end in `_test`. Test rows are rolled back;
the test table remains for subsequent runs. If Composer is installed, `composer test`
also runs them.

## Configuration and deployment

Use a dedicated MySQL account with access limited to this application's database.
Keep real credentials out of version control and back up the MySQL database.
Due dates support MySQL's range of `1000-01-01` through `9999-12-31`.

Configure your web server's document root to **`public/`**, never the repository
root, so configuration and application files are not publicly accessible. Use HTTPS
and disable PHP's `display_errors` in production; application failures are written
to the PHP error log. The built-in PHP server is for local development only.

This is a **single-user starter** without authentication. All visitors share the
same task list; do not expose it publicly without adding authentication and access
controls. Forms use session-based CSRF tokens, database writes use prepared
statements, and user content is escaped when rendered.
